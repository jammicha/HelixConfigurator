Deploy the Helix OTel gateway to Kubernetes

The configurator generates a self-contained Helm chart — the Helix OTel gateway (and an optional local viewer) pre-wired to your Helix tenant. You helm install it in your cluster, then point your apps at the gateway’s in-cluster Service. This is the full walkthrough behind the in-app Generate Kubernetes deployment step.

1Generate & download the chart

In the configurator’s Generate step (or the dashboard’s Generate Kubernetes deployment action), choose whether to include the local viewer, then click Download chart (.zip). Unzip it and cd into the chart folder — run the rest of these steps from inside it: 

unzip helix-otel-chart.zip
cd helix-otel

Run this from wherever the .zip downloaded — your browser’s download folder, usually ~/Downloads.

The chart is pre-wired from your saved configuration: your HELIX_ENDPOINT and X_SOURCE are baked into values.yaml, and your live collector pipeline becomes the gateway’s ConfigMap. Your API key is never written into the chart — it is supplied at install time (next step).

2Create the Helix API-key secret

Create a Kubernetes Secret holding your Helix API key. The chart references it by name, so the key stays out of the chart files and your version control: 

kubectl create secret generic helix-key \
  --from-literal=HELIX_API_KEY='<TenantID>::<AccessKey>::<SecretKey>'

The configurator pre-fills this command with your live key (run it locally; it’s never sent anywhere). If you’re generating the chart for someone else, tick “Generating this for someone else (omit my key)” and the command ships with a placeholder for them to fill in.

Already manage secrets your way?
Point the chart at an existing Secret instead of creating one: --set helix.existingSecret=<your-secret-name> (it must expose a HELIX_API_KEY key).

3Install with Helm

helm install helix . --set helix.existingSecret=helix-key

Install into a specific namespace by adding -n <namespace> (create it first if needed):

kubectl create namespace observability
helm install helix . -n observability \
  --set helix.existingSecret=helix-key

This brings up the gateway Deployment + Service (named helix-gateway, listening on 4317/4318 with metrics on 8888), and — unless you disabled it — the local viewer (helix-viewer) on a small PVC.

4Point your apps at the gateway

A Kubernetes Service gives the gateway a stable in-cluster DNS name — no bridging required. Point your own collector (or instrumented apps directly) at it.

Option A · You run your own collector

Add the gateway as an exporter in your collector’s ConfigMap, then roll it out:

exporters:
  otlphttp/helix_gateway:
    endpoint: "http://helix-gateway.<namespace>.svc.cluster.local:4318"
    tls:
      insecure: true

service:
  pipelines:
    traces:  { exporters: [..., otlphttp/helix_gateway] }
    metrics: { exporters: [..., otlphttp/helix_gateway] }
    logs:    { exporters: [..., otlphttp/helix_gateway] }
kubectl rollout restart deployment/<your-collector>

Option B · App sends OTLP directly

Set this on your application’s Deployment (replace <namespace> with where you installed the chart):

OTEL_EXPORTER_OTLP_ENDPOINT=http://helix-gateway.<namespace>.svc.cluster.local:4318

Apps running in the gateway’s own namespace can use the short form http://helix-gateway:4318.

Onboarding more than one app?

The gateway uses a shared X-Source header for everything it forwards. To keep apps separate in Helix, give each one a distinct service.namespace so they appear as individual OTel Namespaces rolling up to one Business Service: 

OTEL_SERVICE_NAME=<service-name>
OTEL_RESOURCE_ATTRIBUTES=service.namespace=<app>,deployment.environment=<env>

5Verify telemetry is flowing

The configurator is generate-only — it doesn’t reach into your cluster — so verify from your own kubectl and in Helix.

Gateway pods are up

kubectl get pods -l app.kubernetes.io/component=gateway -n <namespace>

Watch it locally (if you included the viewer)

kubectl port-forward svc/helix-viewer 3001:3001 -n <namespace>

Then open http://localhost:3001/otel-data.

See it in Helix

Open your tenant’s OTel Namespace Overview dashboard — traces, metrics, and logs from your apps should appear within a couple of minutes of pointing them at the gateway.

★Options & flags

  • Local viewer — on by default (a Deployment + PVC). Disable it with --set viewer.enabled=false, or untick it before downloading.
  • Existing secret — --set helix.existingSecret=<name> to reference a Secret you manage yourself.
  • Override the baked endpoint/source at install — --set helix.endpoint=… --set helix.xSource=….
  • OpenTelemetry Operator flavor — coming soon: an OpenTelemetryCollector CR + zero-code auto-instrumentation, for clusters that already run the Operator.

?Troubleshooting

Viewer pod stuck in ImagePullBackOff on a local cluster

The viewer uses the local configurator image. On kind/minikube, load it into the cluster first:

kind load docker-image helix-configurator:latest
# or:
minikube image load helix-configurator:latest
OpenShift / restricted Pod Security
The gateway runs fully non-root and passes the restricted Pod Security Standard. The local viewer image currently runs as root — on OpenShift or a restricted-PSA namespace it needs a non-root image rebuild or a namespace exception. If that’s a blocker, install with --set viewer.enabled=false and use Helix (or port-forward from a permissive namespace) to view data.
